# PythonOS Architecture

## Principle: Linux kernel, Python everything else

```
Linux kernel  (C, the one exception)
     |
initramfs     (busybox + python3, minimal userspace to bootstrap)
     |
PythonOS init (system/init/pyinit.py — Python, PID 1)
     |
system services (Python, JSON-defined units in system/services/)
     |
shell / desktop session (Python)
```

The kernel is native because rewriting a Linux-compatible kernel in Python
is not a reasonable goal for this project and Linux already solves hardware
support, scheduling, memory management, and drivers. Everything Linux hands
control to is Python.

## Init

`system/init/service.py` defines a `Service` (name, exec_start, depends_on,
restart policy) loaded from JSON unit files, and a topological sort
(`resolve_start_order`) that raises `DependencyError` on missing
dependencies or cycles.

`system/init/manager.py` implements `ServiceManager`: starts services in
dependency order, reaps dead children via `waitpid`, and restarts services
that exit unexpectedly up to `restart_max` times. It's built against a
`ProcessLauncher` interface so the scheduling/restart logic can be unit
tested (`tests/unit/test_init_manager.py`) without real forking.

`system/init/pyinit.py` is the thin PID-1 entrypoint: mounts `/proc`,
`/sys`, `/dev` when actually running as PID 1 (a no-op elsewhere, e.g. under
test), loads `ServiceManager` against a services directory, and loops
reaping children until it receives SIGTERM (shutdown) or SIGUSR1 (reboot).

This has been boot-tested for real under QEMU against a genuine Linux
kernel — see [BOOT.md](BOOT.md).

## Shell (pysh)

`shell/core.py` implements a `Shell` class: a pipeline parser (`|`,
`>`, `>>`, `<`, `$VAR` expansion, aliases) and an executor that dispatches
to Python-native builtins (cd, pwd, ls, cp, mv, rm, mkdir, cat, ps, kill,
history, alias, export, echo, help, clear) or falls through to
`subprocess`-based external command execution with real pipe wiring
between stages. See [SHELL.md](SHELL.md).

## What's not built yet (see ROADMAP.md)

Desktop, package manager, installer, and full system services (users,
network, audio, power) are not implemented. Do not assume they exist;
ROADMAP.md is authoritative.

## Known constraints of the current development container

- No GPU/display attached — desktop/graphical work needs a virtual
  framebuffer (Xvfb, or a QEMU VGA console) before it can be developed
  against; this is why Phase 5+ is `PLANNED`, not started.
- The kernel used for boot-testing is the distro's `linux-image-generic`
  package rather than a from-source PythonOS-configured kernel; that's a
  reasonable starting point (it's a real, unmodified Linux kernel) and can
  be replaced with a custom build later without changing anything above
  the initramfs layer.
